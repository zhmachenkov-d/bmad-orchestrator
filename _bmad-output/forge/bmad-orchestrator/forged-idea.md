# Forged idea: orch — multi-project orchestration module for BMad

Outcome: HARDENED (2026-09-25). Input for `bmad-module-builder` (Ideate Module).

## Niche
Multi-project (monorepo + polyrepo) feature delivery for teams already working in BMad (PRD → architecture → epics/stories → `bmad-build`), with several people working in parallel without merge hell or stale artifacts. Not a replacement for AI-DLC; it is BMad-native. Its edges over AI-DLC (polyrepo team work, package-level nodes in a monorepo, verifiable canonical contracts) are a head start, not a moat.

## Locked decisions
1. **Enforcement is deterministic git gating, not prompts.** Each story runs in its own branch/worktree. `orch-gate` (a uv script, identical in CI) checks the diff against `allowed_write`, contract conformance, pinned hashes, and sprint-status consistency before merge. Client hooks (e.g. PreToolUse) are optional hardening.
2. **Read isolation exists to save context, not for security.** The node context includes imported contracts plus `allowed_read`, with an instruction not to read outside it. There is no physical isolation (sparse checkout).
3. **Contract-first.** The contract change is the first story of an epic, in the pseudo-subproject `contracts`. Implementation stories build against the merged contract. A contract error sends work back to a contract story; nodes never negotiate with each other directly.
4. **Coordination repo + code repos is the single abstraction.** A monorepo is the degenerate case where both are the same repo. Claims, shards, the registry, and canonical contracts all live in the coordination repo.
5. **Canonical contracts live in the coordination repo** (`contracts/<subproject>/...`). Services hold copies or generated code, and the gate checks conformance. The accepted cost: a service team cannot change its API alone; changes go through a contract story + CODEOWNERS.
6. **Epic = cross-cutting value; story = exactly one subproject** (`subproject:` tag). Stories carry explicit `depends_on`, which points only backwards per the stock BMad rule, so the graph has no cycles. The **story DAG** schedules work. The subproject DAG (registry `imports`) only validates the plan.
7. **A dependency is satisfied when the story is merged to main.** No stacked branches. Idle time during review is reduced by keeping stories small.
8. **No roles in the module.** Authorization is delegated to the git host (CODEOWNERS + branch protection on `contracts/` and planning artifacts). Consistency comes from: claims as git refs (`refs/heads/claim/...`, atomic `update-ref`), pinning contract/PRD hashes in stories and branches, and sharded state (each clone writes only its own file).
9. **Concurrent contract changes are optimistic:** there is no lock. Closing a contract story means rebasing onto the latest contract and re-approving.
10. **Never fork stock BMad skills.** Integration happens only via `_bmad/custom/*.toml`:
    - `bmad-create-epics-and-stories`: `persistent_facts` carries the registry list and the story rules.
    - `bmad-build`: `activation_steps_prepend` / `persistent_facts` inject the node context; `on_complete` writes a completion shard.
    - Checkpoint: about 4 overrides per stock skill at most; beyond that, fork.
11. **`sprint-status.yaml` is derived from shards.** A custom git merge driver (`.gitattributes`) rebuilds it on conflict. The gate rejects divergence in clones where the driver is not registered.
12. **Module shape follows the official BMad Builder conventions.**
    - Module code `orch`; the `bmad-` prefix is reserved.
    - Skills: `orch-setup` (generated by Create Module, plus our steps: merge driver, custom TOMLs, registry validation), `orch-next` (ready story → claim → worktree → node context → `bmad-build`), `orch-gate`, `orch-status`.
    - No agents. Scripts live in each skill's `scripts/` and run with `uv run` (PEP 723).
    - Registration: `orch-setup/assets/module.yaml` + `module-help.csv`.
    - Distribution: `.claude-plugin/marketplace.json` + `npx bmad-method install --custom-source`.
    - Build path: IM → BW per skill → CM → VM.
13. **Registry:** one YAML file per subproject at `orch/subprojects/<name>.yaml` in the coordination repo:
    ```yaml
    name: payment-service
    repo: .                # "." for a monorepo, a git URL for a polyrepo
    path: services/payment-service
    allowed_read: ["services/payment-service/**", "contracts/**"]
    allowed_write: ["services/payment-service/**"]
    contracts:
      exports: [{ type: openapi, canonical: contracts/payment-service/openapi.yaml,
                  copy: services/payment-service/docs/openapi.yaml }]
      imports: [user-service]
    ```

## Rejected
- YAML workflow DSL (`type: loop`, `run-script`), `bmad.module.json`, `agents/*.md`, a `bmad-builder validate` CLI, `npx skills add`, `src/`: none of these exist in BMad.
- Prompt-only boundaries: a wish, not a guarantee.
- Executing in topological order of the subproject graph: consumers drive contracts, and it serializes work needlessly.
- The "cross-cutting story + per-node slices" model: the user wants stories scoped to one subproject.
- Stacked branches: cascading rebases are just merge hell again.
- A role/permission system inside the module: prompt-level security; the git host already does this.
- Switching to AI-DLC: it would force BMad teams to leave their artifacts behind.
- `bmad-*` naming, `$schema` on a bmad domain, `workspace.driver`, manifests living inside services.

## Open
- **Unverified:** that the first user already lives in BMad. The whole niche depends on this, and no pilot project has been named yet.
- Supporting both monorepo and polyrepo in v1 (chosen against the recommendation to start monorepo-only). Risk: every mechanism needs cross-repo gating and claims.
- Polyrepo merge ordering: coordinating N PRs across repos by feature-id still has no design.
- Stock-skill override count: watch against the fork threshold.
