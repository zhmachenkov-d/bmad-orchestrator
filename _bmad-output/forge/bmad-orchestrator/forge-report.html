orch — multi-project orchestration for BMad

Forge session for Denys Zhmachenkov · goal: test the idea and make it better · outcome: Hardened

Next step: bmad-module-builder → Ideate Module, using forged-idea.md

Outcome

The original spec assumed a runtime that does not exist in BMad: a YAML workflow DSL, bmad.module.json, a validator CLI, and the bmad- prefix. What survives is a BMad-native module with four skills (orch-setup, orch-next, orch-gate, orch-status). Its guarantees come from deterministic git gating, not prompts. Work is contract-first. Stories are scoped to one subproject and scheduled by an explicit story DAG. Multi-user safety comes from git-ref claims, hash pinning, and sharded state, with no roles in the module. Polyrepo needs no merge train: breaking contract changes go through expand → migrate → contract, and merge status is read from a .orch/stories/<story>.yaml marker in each code repo. The niche is teams already living in BMad; that is also its main unverified assumption.

Locked decisions

  1. Git-level gate: each story gets its own branch or worktree, and orch-gate checks the diff against allowed_write, contract conformance, and hash pins before merge. Client hooks are optional.
  2. Read isolation saves context; it is not security. The node context is imported contracts plus allowed_read.
  3. Contract-first: the contract change is the first story of an epic, in the pseudo-subproject contracts.
  4. One abstraction: coordination repo + code repos. A monorepo is the degenerate case.
  5. Canonical contracts live in the coordination repo. Services hold copies, and the gate checks conformance.
  6. Epic = cross-cutting value; story = exactly one subproject. Explicit depends_on forms a story DAG, which schedules the work.
  7. A dependency is done when it is merged to main. No stacked branches.
  8. No roles. Authorization goes to CODEOWNERS; consistency comes from claims (git refs), hash pinning, and sharded state.
  9. Concurrent contract edits are optimistic: rebase and re-approve.
  10. Stock BMad skills are never forked; integration is only via _bmad/custom/*.toml.
  11. sprint-status.yaml is derived from shards, using a custom merge driver plus a gate backstop.
  12. Official BMad Builder shape: code orch, no agents, uv scripts per skill, marketplace.json, built via IM → BW → CM → VM.
  13. Registry: orch/subprojects/<name>.yaml in the coordination repo, with allowed_read kept.
  14. No breaking contract change in one step: expand → migrate → contract, with the gate detecting breaking changes. Dependent PRs are ordered by readiness; independent PRs merge in any order.
  15. Merge status is derived and pull-based: the coordination repo needs only read access to code repos, with no cross-repo write tokens.
  16. Merge marker is a file: .orch/stories/<story>.yaml with contract pins, which survives merge, squash and rebase.

Rejected, and why

  • YAML workflow DSL, bmad.module.json, agents/*.md, validator CLI, npx skills add, src/: none of these exist in BMad or BMad Builder.
  • Prompt-only boundaries: a wish, not a guarantee.
  • Executing in topological order of subprojects: consumers drive contracts, and it serializes work needlessly.
  • Cross-cutting story + per-node slices: the user wants stories scoped to one subproject.
  • Stacked branches kill: cascading rebases are merge hell again.
  • A role/permission system in the module: prompt-level security; the git host already provides this.
  • Switching to AI-DLC: it would force BMad teams to abandon their artifacts.
  • bmad-* names, $schema on a bmad domain, workspace.driver, manifests inside services.
  • Merge train across repos kill: fragile, and a half-merged rollback is manual.
  • Push receipts from service CI: needs write tokens on canonical contracts and loses events.
  • Orch-Story commit trailer kill: squash and rebase merges rewrite it.

Weak points that survived

  • Unverified niche: no pilot project has been named, and "first user already lives in BMad" is still an assumption.
  • Monorepo + polyrepo both in v1 (chosen against the recommendation): every mechanism needs a cross-repo variant.
  • Breaking-change detectors per contract type: OpenAPI is covered; AsyncAPI, protobuf and DB schemas each need a tool.
  • Override creep on bmad-build and bmad-create-epics-and-stories: the fork threshold is about 4.
  • Merge-driver registration is per clone; the gate is the only backstop.
